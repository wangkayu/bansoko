# PostgreSQL gate shard assignment: which package runs in which container job.
#
# The container lane (`.github/workflows/ci.yml`, jobs `postgres-integration-shard-N`)
# runs three jobs in parallel; each one passes `BANSOKO_TEST_PG_SHARD=<n>/3` to
# `scripts/ci/test-integration.sh`, which selects exactly the packages assigned to
# that shard here. Without the variable the script still runs the full set, so
# host-runner and local runs are unchanged.
#
# This file and `scripts/ci/postgres-packages.txt` must describe the same set:
# `scripts/ci/check-ci-shards.sh` fails closed on a missing, duplicated or unknown
# package, on a shard outside 1..3, and when the workflow does not ask for
# exactly these three shards.
#
# Assignment follows the VM per-package `ok` durations measured 2026-10-19 with the
# template-database reset (task 10-19-faster-gates): fileoperation/application 499s,
# runtime/migrations 357s, filemaintenance 59s, rss/application 37s, everything else
# under 25s. `internal/fileoperation/application` is filesystem-bound (xfs on the
# container lane is ~2x the VM's filesystem), so it is the whole of shard 1 and the lane's
# floor. Shards 2 and 3 are balanced to ~380s / ~350s on the VM: `runtime/migrations`
# keeps shard 2 (database-bound, replays real migrations) and the DB-bound
# application packages moved to shard 3 next to the filesystem-heavy ones.

# shard 1: the single longest package, which sets the floor for the lane.
1	./internal/fileoperation/application
